# 会议进程发现与刷新退出排查

## 已确认的现象

本机只读检查可发现 `wemeetapp.exe` 主进程及子进程，原有 `meeting_processes()` 也能返回候选；不是“腾讯会议完全没有启动”。Windows Application 日志记录了原知识库轻量包 EchoMind.exe 在 ucrtbase.dll 的 `0xc0000409` 原生退出。该错误记录本身不能确定具体 Python 调用栈；未把它直接等同于权限错误或某个依赖损坏。

新增回归在旧代码中复现了三个独立缺陷：切回会议来源不自动刷新、点击开始沿用旧 PID、刷新线程闭包持有整个窗口。进一步的打包运行库测试发现，销毁后的窗口还被变量 trace 回调保留。后两项属于 Tk 对象生命周期风险，不能仅靠捕获 Python 异常处理。

## 针对性修改

- 切回腾讯会议自动刷新；开始采集先异步更新候选，再自动选择主进程并启动。没有主进程时不启动，也不要求用户操作已移除的 PID 下拉框。
- 查找期间有状态反馈和停止取消入口，不允许反复创建刷新任务；取消后到达的结果不再启动采集。
- 刷新工作线程仅持有查询函数和结果队列，不持有 Tk 窗口；销毁时移除三处变量 trace，避免保留界面对象。
- PowerShell 枚举上限 8 秒，失败回到可重试状态，不使用旧候选继续启动。
- 增加本地 faulthandler 日志，记录致命堆栈以便原生退出再次出现时继续定位。不记录密钥、录音、转写、题库或回答，不自动上传。日志不可写时不阻止应用启动。

## 验证边界

完整回归 732 项通过，另对最终 trace 清理修改重跑了相关界面测试。最终修复包的运行库完成 22 次真实本机进程查询，均自动选中主进程；采集启动使用替身，只检查传入 PID，不实际录音。刷新尚在等待时销毁窗口，验证窗口对象在主线程释放、后台仅返回普通数据且不再持有窗口，此测试通过。主 EXE 在隐藏测试桌面等待自动刷新并保持 15 秒后正常退出。最终包位于 `dist/light-v0.1.3-process-recovery/EchoMind`，未覆盖旧包。

原日志所示的相同原生崩溃尚未稳定复现，不能宣称该退出码所有成因均已消除。以上修复覆盖了已复现缺陷，后续真实使用若仍退出，应结合 `%LOCALAPPDATA%\EchoMind\logs\native-crash.log` 继续排查，而不是让用户反复重装组件。
